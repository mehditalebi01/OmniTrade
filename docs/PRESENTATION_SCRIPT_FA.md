# سناریو و متن ارائهٔ OmniTrade AI

متن فارسی برای ارائهٔ درس Software Engineering؛ لحن گفتاری و دوستانه، بر اساس کد و مستندات موجود در ۱۴ سپتامبر ۲۰۲۶.

این راهنما سناریوی ارائه است؛ در تهیهٔ آن اپلیکیشن اجرا نشده، اتصال خارجی بررسی نشده و تست‌ها دوباره اجرا نشده‌اند. زمان پیشنهادی با دمو حدود ۳۰ تا ۴۰ دقیقه است؛ برای جلسهٔ کوتاه‌تر، نسخهٔ ۱۵ دقیقه‌ای انتهای فایل را دنبال کنید. متن داخل گیومه برای گفتن است؛ بخش «روی صفحه» دستور اجرای دمو است.

## قبل از شروع جلسه

- از قبل `docker compose up --build -d` را در پوشهٔ پروژه اجرا کنید و ورود در `http://localhost:5173` را بررسی کنید. حساب دمو طبق README برابر `demo / demo` است.
- مدل و منابع دادهٔ موردنیاز را در همان جلسهٔ سرور ذخیره و Verify کنید. راه‌اندازی مجدد API می‌تواند اتصال‌های نگه‌داری‌شده در حافظه را از بین ببرد؛ قبل از ارائه دوباره بررسی کنید.
- یک تحلیل واقعی موفق و PDF و JSON آن را برای روز ارائه آماده داشته باشید. اگر از خروجی قبلی استفاده شد، تاریخ و قبلی بودن آن را واضح بگویید.
- برای نمونهٔ اصلی AAPL، هر چهار تحلیلگر، عمق ۲، ریسک Balanced، زبان English یا Italian و ارز USD مناسب یک دموی ساده‌اند. این انتخاب برای نمایش نرم‌افزار است، نه پیشنهاد سرمایه‌گذاری. انتخاب نهایی باید با اتصال‌های واقعاً در دسترس سازگار باشد.
- بودجهٔ پیش‌فرض فرم را نگه دارید و یک بار همین ترکیب را پیش از جلسه تمرین کنید. زمان پاسخ مدل یا سرویس بیرونی را نمی‌توان تضمین کرد.
- Workflow Lab را پیش از جلسه Validate و Publish کنید. تغییرات آزمایشی ارائه را در پایان اصلاح و دوباره Publish کنید.
- در ویرایشگر، فایل‌های `contracts.py`، `engine/catalog.py`، `engine/validator.py`، `engine/runtime.py`، `services.py` و یک تست مربوط را آماده کنید. مسیر کامل این فایل‌ها در جدول انتهایی آمده است.
- برای بخش طراحی، نمودارهای Use Case، Component، Sequence، State و Deployment را از پوشهٔ `modeling/visual-paradigm/uml-v7` آماده کنید.
- ورود کلید را پیش از اشتراک صفحه انجام دهید؛ در دمو وضعیت اتصال و نام مدل را نشان دهید.

## ۱. معرفی و مسئله — حدود ۲ دقیقه

**روی صفحه:** وارد شوید و Overview را نشان دهید.

**بگو:**

«سلام استاد. امروز می‌خوام OmniTrade AI رو با یک مثال کامل نشون بدم؛ از وقتی کاربر منابع و روش تحلیلش رو انتخاب می‌کنه، تا وقتی یک گزارش قابل بررسی دریافت می‌کنه.

مسئله‌ای که داریم اینه که اطلاعات یک سهم پراکنده‌ست: قیمت و حجم یک جاست، اطلاعات شرکت جای دیگه، خبرها و شرایط اقتصاد هم جدا هستن. تازه این اطلاعات ممکنه قدیمی باشن، با هم تناقض داشته باشن یا یکی از منابع جواب نده.

ما یک سیستم ساختیم که این داده‌ها رو در یک workflow مشخص جمع می‌کنه، به نقش‌های تحلیلی مختلف می‌ده، دیدگاه مثبت و منفی رو بررسی می‌کنه و بعد از ارزیابی ریسک، گزارش می‌سازه. کاربر هم می‌تونه روند و تنظیماتش رو تغییر بده و بفهمه خروجی از کجا اومده.

محدودهٔ پروژه تحلیل سهامه. سیستم سفارش خریدوفروش ثبت نمی‌کنه و اتصال بروکر یا مدیریت واقعی پرتفوی نداره؛ خروجی‌اش برای پشتیبانی از تصمیمه.»

**نشان بده:** پنج شاخهٔ داده، مسیر Configure تا Report، گزارش‌های اخیر و دکمهٔ شروع تحلیل. نقش «Portfolio Manager» در برنامه نام یک نقش تصمیم‌گیری است، نه قابلیت مدیریت حساب بورسی.

**جملهٔ اتصال:** «اول ورودی‌های سیستم رو مشخص می‌کنم، بعد خود روش تحلیل رو تغییر می‌دم.»

## ۲. Connections؛ اتصال واقعی مدل و داده — حدود ۳ دقیقه

**روی صفحه:** Connections → انتخاب یک ارائه‌دهندهٔ موجود → نام مدل یا تنظیمات لازم → Save session connection → Verify now. اگر اتصال قبلاً آماده است، Verify را نشان دهید و از ورود دوبارهٔ کلید صرف‌نظر کنید.

**بگو:**

«اینجا دو نوع اتصال داریم: سرویس مدل زبانی و سرویس داده. این دو نقش متفاوت دارن؛ یکی دادهٔ مالی می‌ده و دیگری به توضیح تحلیل کمک می‌کنه.

صرف وارد کردن کلید کافی نیست. اتصال باید ذخیره و بررسی بشه تا برای استفاده در فرم تحلیل در دسترس قرار بگیره. اگر سرویس اجازهٔ دسترسی نده یا محدودیت درخواست داشته باشه، خطا رو می‌بینیم.

برای مدل، بسته به ارائه‌دهنده، API key، آدرس سازگار، شناسهٔ مدل یا اطلاعات مخصوص اون سرویس تنظیم می‌شه. مثلاً Bedrock منطقهٔ AWS و شناسه‌های مجاز مدل رو هم داره. اگر چند مدل در دسترس باشن، می‌تونم بعداً مدل سریع و مدل عمیق رو جدا انتخاب کنم.

اطلاعات محرمانهٔ این اتصال‌ها در حافظهٔ API برای جلسهٔ سرور نگه‌داری می‌شن؛ داخل گزارش و تاریخچهٔ تحلیل ذخیره نمی‌شن.»

**روی صفحه:** Load available models، اگر برای ارائه‌دهنده فعال است؛ سپس Connect supported keyless sources و وضعیت منابع داده.

**بگو:**

«برای داده، Yahoo Finance و Polymarket مسیر اتصال بدون کلید دارن. FRED و Alpha Vantage تنظیمات خودشون رو دارن. Reddit و StockTwits هم منابع عمومی اختیاری هستن که ممکنه دسترسی عمومی‌شون رد بشه؛ فعال بودنشون رو فرض نمی‌کنیم.

هر منبع فقط برای نقش‌هایی پیشنهاد می‌شه که پشتیبانی می‌کنه. مثلاً FRED و Polymarket در نقش macro قرار می‌گیرن. در New Analysis نقشهٔ این قابلیت‌ها رو می‌بینیم.

اگر برای یک نقش چند منبع تأییدشده انتخاب کنم، یک زنجیرهٔ fallback داریم: وقتی منبع اول شکست بخوره، نوبت منبع بعدی منتخب می‌شه. این انتخاب به معنی ادغام خودکار پاسخ همهٔ منابع نیست.»

**پوشش تکمیلی:** دکمهٔ Remove را معرفی کنید؛ اتصال موردنیاز دمو را حذف نکنید. کاتالوگ مدل‌ها شامل OpenAI، Gemini، Anthropic، xAI، DeepSeek، Qwen، GLM، MiniMax، OpenRouter، Mistral، Kimi، Groq، NVIDIA NIM، Azure OpenAI، Bedrock، Ollama و سرورهای سازگار است. همه را تک‌تک Verify نکنید و ادعا نکنید همه امروز آزمایش شده‌اند.

**اگر Verify شکست خورد:** «این اتصال الان در دسترس نیست. این هم بخشی از رفتار واقعی سیستم با وابستگی خارجیه. برای ادامه از اتصال تأییدشدهٔ موجود استفاده می‌کنم.»

## ۳. Profile؛ شخصی‌سازی دارای اثر — حدود ۲ دقیقه

**روی صفحه:** Profile؛ نام نمایشی، نماد پیش‌فرض، مدل‌های پیش‌فرض و Investment Policy را نشان دهید. یک مقدار مناسب دمو را تغییر دهید و Save profile بزنید.

**بگو:**

«این صفحه هم پیش‌فرض‌های فرم رو نگه می‌داره، هم سیاست سرمایه‌گذار رو. اسم و ایمیل صرفاً اطلاعات پروفایل هستن؛ روی توصیه اثر ندارن.

ولی افق زمانی، سطح تجربه، حداکثر زیان قابل قبول، سقف اندازهٔ موقعیت و بخش‌های مستثناشده، ورودی‌های واقعی اجرای تحلیل هستن. افق زمانی روی آستانه‌های تحلیل اثر می‌ذاره، محدودیت زیان وارد بررسی ریسک می‌شه و سقف موقعیت در راهنمای تصمیم لحاظ می‌شه. سطح تجربه هم برای نحوهٔ توضیح دادن به مدل ارسال می‌شه.

اگر بخش فعالیت شرکت در فهرست بخش‌های ممنوع باشه، منطق برنامه می‌تونه نتیجهٔ BUY رو مسدود کنه. یعنی این شخصی‌سازی فقط عوض کردن ظاهر صفحه نیست.

این تنظیمات داخل هر اجرا کپی می‌شن تا بعداً معلوم باشه گزارش با چه سیاستی ساخته شده.»

**برای نمایش اثر واقعی:** دو گزارش از قبل آماده‌شده با سیاست متفاوت را در پایان مقایسه کنید. تضمین نکنید تغییر هر گزینه حتماً BUY را به SELL تبدیل می‌کند؛ بعضی تغییرات روی متن یا آستانه اثر دارند و ممکن است نتیجهٔ نهایی ثابت بماند.

## ۴. Workflow Lab؛ معرفی روند کامل — حدود ۳ دقیقه

**روی صفحه:** Workflow Lab، نمای کلی گراف و سپس بزرگ‌نمایی روی شاخه‌ها.

**بگو:**

«اینجا روش تحلیل به‌صورت گراف نمایش داده می‌شه. هر نود یک مسئولیت مشخص داره و هر اتصال، انتقال یک نوع مشخص از ورودی یا خروجیه.

اول نماد سهم resolve می‌شه. بعد پنج شاخهٔ دادهٔ بازار، fundamentals، خبر، macro و sentiment داریم. داده‌ها normalize می‌شن؛ یعنی به قرارداد مشترک تبدیل می‌شن. اندیکاتورهای تکنیکال و نسبت‌های مالی هم محاسبه می‌شن.

در Join، ورودی‌ها جمع می‌شن و از کنترل زمان و کیفیت می‌گذرن. بعد چهار تحلیلگر تخصصی انتخاب‌شده دیدگاهشون رو می‌سازن. Macro در این طراحی یک شاخهٔ داده‌ست و تحلیلگر پنجم مستقلی در فرم نداره.

مرحلهٔ پژوهش، دیدگاه Bull و Bear و مدیریت بحث رو داره. عمق بحث محدوده؛ قرار نیست یک حلقهٔ بدون پایان داشته باشیم. بعد proposal ساخته می‌شه، سه دیدگاه ریسک aggressive، balanced و conservative بررسی می‌شن و نتیجه از اعتبارسنجی تصمیم به تولید گزارش می‌رسه.

پس گراف فقط تصویر معماری نیست؛ تعریف اجرایی فراینده.»

**نکتهٔ دقیق:** گراف مرجع در `sample_workflow.py` دارای ۳۳ نود است. این عدد را برای همهٔ گراف‌های شخصی‌سازی‌شده ثابت معرفی نکنید؛ تعداد نوع‌های کاتالوگ، نودها و نقش‌های تحلیلی یکی نیست.

## ۵. ویرایش گراف و نمایش Invalid Cases — حدود ۴ دقیقه

**روی صفحه، به همین ترتیب:**

1. یک نود را انتخاب کنید؛ توضیح What this node does و نوع آن را نشان دهید.
2. نام آن را مثلاً به «Market review for demo» تغییر دهید، رنگ را عوض کنید و Apply name/color بزنید.
3. نود را جابه‌جا کنید؛ Undo و Redo را نشان دهید. میان‌برهای Ctrl+Z و Ctrl+Y هم موجودند.
4. Smart next nodes را نشان دهید؛ توضیح دهید پیشنهادها از سازگاری پورت‌ها می‌آیند.
5. برای نمونهٔ اتصال نامعتبر، خروجی Fetch Market را به Report Renderer وصل کنید. این دو نوع ورودی/خروجی سازگار ندارند؛ پیام منع اتصال باید ظاهر شود و یال وارد گراف نشود.
6. برای خطای ساختاری، یک Start دوم از Node catalog اضافه کنید و Validate بزنید. انتظار: خطای تعداد Start و احتمالاً خطای نود دسترس‌ناپذیر. Undo کنید و دوباره Validate بزنید.
7. دکمه‌های Delete و Reset node را معرفی کنید. اگر آن‌ها را اجرا می‌کنید، تغییر را با Undo برگردانید. Reset node نام و رنگ را بازمی‌گرداند؛ آن را بازنشانی همهٔ پارامترهای اجرایی نود معرفی نکنید.
8. گراف اصلاح‌شده را Save، Validate و Publish کنید؛ وضعیت معتبر را نشان دهید.

**بگو:**

«دو سطح کنترل داریم. اینجا یک اتصال ناسازگار همون موقع رد می‌شه. ولی برای معتبر بودن کل گراف، فقط سازگار بودن یک یال کافی نیست؛ تعداد Start و End، دسترسی نودها، ورودی‌های لازم، حلقه‌ها و بودجه هم باید بررسی بشن.

خطایی که الان ساختم عمدیه. می‌خوام نشون بدم سیستم علاوه بر مسیر موفق، جلوی تعریف ناقص یا ناامن فرایند رو هم می‌گیره. خطا فقط یک عبارت کلی نیست؛ کد و در صورت نیاز شناسهٔ نود یا یال داره.

Save یعنی نگه‌داشتن Draft. Validate یعنی بررسی تعریف فعلی. Publish نسخهٔ قابل اجرا رو می‌سازه. هر اجرا به نسخهٔ منتشرشدهٔ خودش متصله، پس تغییر Draft نباید معنی یک گزارش قدیمی رو عوض کنه.»

**پوشش تکمیلی:** Reset graph پیش‌نویس پیش‌فرض کامل را برمی‌گرداند و نسخه‌های منتشرشده و گزارش‌های قدیمی را نگه می‌دارد. دکمه پیام تأیید خود برنامه را دارد. Add از کاتالوگ، Add از پیشنهادها، حذف یال، MiniMap و کنترل زوم را هم کوتاه نشان دهید. یک پیشنهاد سازگار به‌تنهایی اعتبار کل گراف را تضمین نمی‌کند.

**مرز مهم برای دفاع:** در UI فعلی، تغییر نام، رنگ، موقعیت، وجود نود و اتصال‌ها فراهم است. تنظیمات داخلی مثل `failure_policy`، timeout، retry هر نود و `join_policy` در قرارداد و موتور وجود دارند، اما پنل عمومی ویرایش همهٔ آن‌ها در Workflow Lab دیده نمی‌شود. آن‌ها را در بخش کد توضیح دهید، نه به‌عنوان کنترل موجود در صفحه.

## ۸. Run History؛ Pause، Resume و Cancel — حدود ۲ دقیقه

**روی صفحه:** Run History؛ اجرای فعال را انتخاب و Pause کنید. پس از مشاهدهٔ paused، Inspect checkpoint و سپس Resume from checkpoint را نشان دهید.

**بگو:**

«Pause یک توقف امنه. درخواست ثبت می‌شه و موتور در مرز امن، بعد از پایان batch جاری، checkpoint می‌سازه و متوقف می‌شه؛ قطع فوری وسط یک فراخوانی خارجی نیست.

در Resume، خروجی نودهای تکمیل‌شده از checkpoint حفظ می‌شه و کار ناتمام ادامه پیدا می‌کنه. این برای اجرای طولانی یا قطع worker مهمه، چون لازم نیست تمام مراحل موفق از صفر تکرار بشن.

Cancel با Pause فرق داره؛ برای لغو نهایی کاره. اجرای cancelled قابل ادامه نیست. Resume برای وضعیت‌های مجاز مثل paused، failed و interrupted در نظر گرفته شده.»

**برای Cancel:** از اجرای آزمایشی جداگانه استفاده کنید یا فقط دکمه و رفتار را توضیح دهید؛ اجرای اصلی لازم برای گزارش را لغو نکنید. اگر اجرا پیش از Pause تمام شد، یک اجرای paused آماده یا شواهد کنترل‌شده را نشان دهید و نگویید همین اجرای تمام‌شده را pause کرده‌اید.

## ۱۰. یک مسیر خطا و بازیابی قابل دفاع — حدود ۲ دقیقه

**توضیح خطاهای کیفیت:** «شواهد مربوط به آینده رد می‌شن. شواهد اصلی بازار یا شرکت هم نمی‌تونن صرفاً با روشن کردن Allow degraded از کنترل تازگی عبور کنن. برای خبر، sentiment یا macro قدیمی، وقتی سیاست اجازه بده، داده از مسیر تحلیل کنار گذاشته می‌شه و هشدار ثبت می‌شه.»

## ۱۱. معماری و UML؛ اتصال محصول به درس — حدود ۳ دقیقه

**روی صفحه:** ابتدا Use Case، بعد Component یا Deployment و سپس Sequence. همهٔ نمودارها را طولانی شرح ندهید؛ هرکدام را به دمو وصل کنید.

این تفکیک کمک می‌کنه قرارداد هر بخش، رفتار خطا و مسئولیت‌ها معلوم باشه. مثلاً تغییر یک ارائه‌دهندهٔ داده نباید الگوریتم scheduler رو عوض کنه.»

## ۱۲. نمایش کد؛ سهم پیاده‌سازی خودمان — حدود ۴ دقیقه

**روی صفحه:** فایل‌ها را به ترتیب زیر باز کنید. کل فایل را اسکرول نکنید؛ تابع مشخص را پیدا کنید.

**الف ـ قراردادها و کاتالوگ**

«در `contracts.py` ساختارهای WorkflowDefinition، NodeDefinition، Run، Budget، Checkpoint و eventها تعریف شدن. در `engine/catalog.py` هر نوع نود ورودی، خروجی و مشخصات خودش رو داره. پیشنهاد اتصال در UI هم از همین اطلاعات تغذیه می‌شه.»

**ب ـ `WorkflowValidator.validate`**

«اینجا همون خطای Start دوم و اتصال نامعتبر رو می‌بینیم. validator تعداد Start و End، پورت‌ها، دسترسی نودها، چرخهٔ بدون حد، ورودی‌ها و بودجه رو بررسی می‌کنه. الگوریتم تشخیص cycle با indegree و پیمایش گراف انجام می‌شه. پیچیدگی اصلی پروژه از ترکیب این محدودیت‌ها میاد، نه صرفاً از یک پیمایش گراف.»

**هـ ـ تست متناظر**

**جمع‌بندی سهم فنی در یک جمله:**
